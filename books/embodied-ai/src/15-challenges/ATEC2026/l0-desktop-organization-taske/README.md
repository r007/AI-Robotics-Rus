# ATEC2026, трек 2 L0 «Уборка стола», Task E: разбор после соревнования

Этот документ описывает полный путь участия в Task E трека 2 L0 «Уборка стола» онлайн-этапа ATEC2026. Задача: манипулятор Piper распознаёт три случайно расставленных предмета, захватывает их и кладёт в указанную корзину. Наш лучший онлайн-результат — `15.00`, это не максимальный балл. Ценность открытого каталога — в честном разборе инженерного пути, сохранённом каркасе отправки и записях неудачных направлений, чтобы другие не повторяли те же ошибки.

## Цель задачи

Основной процесс Task E:

```text
визуальное восприятие -> распознавание и локализация цели -> планирование движения или выход политики -> захват -> перенос -> освобождение над корзиной
```

Онлайн-отправка — загрузка исходного кода в виде файла. Защищённый пакет нашей отправки взят из ветки ACT seed1 best_loss:

```text
code/act_seed1_best_submission/
  solution.py
  act/detr/*.py
  requirements.txt
  run.sh
  server.py
  UPLOAD_README.md
```

Внимание: `policy_act.pt` в GitHub не загружен. Его нужно взять из локального пакета отправки или из репозитория моделей Hugging Face и положить в тот же каталог.

## Какие пути мы пробовали

### 1. Генерация данных скриптованным оракулом

Официальный скриптованный оракул Task E лучше справлялся с объектом `object_3`, но у `object_1` и `object_2` были проблемы: контакт при захвате, несовпадение TCP Piper, различие между корнем USD и геометрическим центром, несоответствие примитивов переноса. В итоге мы сгенерировали демонстрации для трёх объектов, используя примитивы под каждый объект и замкнутое сервоуправление:

```text
datasets/atec_task_e_obj321_servo_100demos
```

Эти данные подходят для обучения ACT, но это не набор правил для контроллера с максимальным баллом.

### 2. ACT / XSA-ACT

ACT оказался самым надёжным путём для отправки. Ключевые исправления:

- исправлена семантика действия Task E: действие равно `(joint_target - default_joint_pos) / 0.5`, а не скорости и не простой дельте;
- `solution_act.py` автоматически загружает `model_args` из checkpoint;
- модификация внимания XSA может служить вариантом ACT, но онлайн-результат нестабилен;
- loss обучения слабо коррелирует с успешностью задачи, поэтому её нужно измерять отдельно для каждого seed.

Результаты онлайн-проверок:

| Вариант | Онлайн-результат |
|---|---:|
| XSA-ACT, загруженная версия | `6.00` |
| ACT seed2 45000 | `12.00` |
| ACT seed2 50000 | `6.00` |
| ACT seed1 best | `15.00` |

Поэтому каталог защищает ACT seed1 best, а не checkpoint seed2, который однажды показал максимальный балл на одном seed.

### 3. GraspNet / AnyGrasp / SAM3 / PCA в стиле GraspGen

Мы подключали и проверяли несколько маршрутов планирования захвата:

- TunTunClaw / GraspNet;
- SDK AnyGrasp;
- сегментация изображений SAM3;
- геометрический захват PCA/AABB в стиле GraspGen;
- центрирование корзины при освобождении;
- подход перед захватом / защищённая вставка;
- «захват с вдвиганием и закрытием» для кубика `object_1`;
- низкое положение cradle/servo для переноса банана `object_3`.

Эти маршруты показали, что восприятие и кандидаты позиций захвата не бесполезны: `object_1` и `object_3` в ряде seed удавалось поднять. Однако итоговый вариант `demo/solution_pca.py` в формате отправки оставался нестабильным в IK, в отслеживании центра пальцев, удержании контакта и освобождении над корзиной, поэтому он не может заменить ACT в финальной отправке.

Важный урок:

```text
AnyGrasp / GraspNet — не контроллер с максимальным баллом «одной кнопкой»;
они дают лишь априорную позу захвата, а дальше нужны IK Piper, калибровка TCP, удержание контакта захвата и примитив освобождения над корзиной.
```

### 4. pi0.5 / OpenPI

Мы системно пробовали pi0.5/OpenPI:

- старая ветка с дополнением до 16D при фиксированной базе;
- ветка с состоянием и действием native8;
- 20 демонстраций / 100 демонстраций;
- LoRA;
- pi05_base;
- сырые неотфильтрованные данные + абсолютное целевое действие;
- ветки action expert / action head;
- нулевой шум / настройка числа шагов выполнения chunk.

Ни одна ветка не превзошла ACT; несколько веток на seed 11/12/13 дали `0/0/0` или очень низкий балл. После соревнования выяснилось, что проблема не в «слабости модели» pi0.5, а в том, что текущее представление данных и моделирование фаз плохо подходят для траекторий Task E:

- фильтрация данных удалила много кадров удержания и стабилизации, что нарушило временную семантику action chunk;
- связь одной камеры и текстового промпта с фазой захвата слабая;
- модель прямого распространения вблизи домашней позиции и высокого положения не имеет непрерывной фазы, поэтому действия дрожат между домашней позицией и средней частью траектории;
- даже при переобучении на одной демонстрации с сырым абсолютным целевым действием в rollout Isaac не получалось устойчивого pick/place.

Поэтому pi0.5 сейчас не рассматривается как кандидат на отправку.

## Почему `policy_act.pt` не хранится в GitHub

`policy_act.pt` весит около 64 МБ. Формально это ниже жёсткого лимита GitHub на один файл, но двоичные веса не нужно хранить в истории учебного репозитория. Рекомендуемый порядок:

1. В GitHub хранить код, README, SHA256 и описание отправки.
2. На Hugging Face хранить веса и полный архив отправки.
3. В README поддерживать ссылки на HF и контрольные значения.

## Можно ли безопасно удалить локальные данные

Можно, но порядок такой:

1. Убедитесь, что каталог уже отправлен в GitHub.
2. Убедитесь, что на Hugging Face загружены `policy_act.pt`, zip отправки, фрагменты данных воспроизведения и журналы.
3. Проверьте, что SHA256 модели, SHA256 фрагментов и SHA256 восстановленного отфильтрованного HDF5 совпадают.
4. Сохраните этот каталог и `docs/workspace-memory-taske-complete-debugging-record.md`.
5. Только после этого удаляйте крупные выходы обучения, `datasets`, `runs`, `logs/videos`, checkpoint openpi в `$PROJECT_ROOT`.

Не удаляйте единственный локальный `policy_act.pt`, пока не убедились, что веса можно скачать с HF.
