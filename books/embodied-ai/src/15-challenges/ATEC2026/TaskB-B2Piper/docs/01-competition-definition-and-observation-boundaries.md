# 1. Определение соревнования и границы наблюдений

## 1.1 Что такое задача

Task B — это задача Garbage Collection (сбор мусора) в ATEC2026 Simulation Challenge; платформа робота — Unitree B2 с манипулятором Piper. Цель не в простой навигации: робот должен найти целевой объект в сцене, подойти к нему, выполнить манипуляцию и доставить объект в указанную мусорную корзину.

Единственным источником определения задачи служит официальный репозиторий:

- [ATEC2026 Simulation Challenge](https://github.com/atecup/ATEC2026_Simulation_Challenge)
- [Официальный каталог Task B](https://github.com/atecup/ATEC2026_Simulation_Challenge/tree/main/source/atec_rl_lab/atec_rl_lab/tasks/task_b)

Параметры задачи, размерность действий, порядок суставов, имена камер и runner официального репозитория могут меняться от версии к версии. Текст этого учебного материала нужен, чтобы выстроить логику решения; реальный запуск всегда нужно делать по той версии официального проекта, которую вы проверили.

## 1.2 Допустимые наблюдения

Публичное описание задачи показывает, что основные входы Task B таковы:

- состояние самого робота и proprioception;
- внешние геометрические наблюдения, например LiDAR;
- головная RGB-D камера для поиска и определения положения дальних целей;
- RGB-D камера на концевом эффекторе для близкого прицеливания и манипуляции.

«Внешний» здесь означает датчик, закреплённый на роботе, а не камеру «всевидящего ока», которая наблюдает за всей сценой. Даже если для отладки в среду добавлена сторонняя камера, это не делает её входом policy.

## 1.3 Запрещённые зависимости

Следующую информацию можно использовать только для локальной диагностики или офлайн-разметки и её нельзя подавать на вход настоящей политики:

| Информация | Почему нельзя |
| --- | --- |
| истинные позы объектов в симуляции | равносильно прямому чтению ответа, обходит проблему восприятия |
| список объектов, соответствующий random seed | ломает обобщение между сценами и может нарушать правила оценки |
| истинная поза робота или ID объектов | это не наблюдаемая датчиком величина |
| изображения глобальной камеры окружения | если её нет в официальном пространстве наблюдений, это не допустимый вход policy |
| внутренние состояния оценщика, например `grasped_objects` | можно использовать для проверки успеха, но нельзя — для решений policy |

При локальной отладке эти величины можно выводить в лог, чтобы ответить на вопрос «почему не удалось захватить». Перед отправкой их нужно убрать из observation, policy, функции награды и условий завершения эпизода.

## 1.4 Почему «привести робота к координатам» недостаточно

Плоская координата цели решает только одну задачу: куда должна ехать база робота. Она не отвечает на вопросы:

1. правильно ли распознана цель;
2. согласуются ли проекции цели в головной и концевой камерах;
3. откалиброваны ли преобразования между базой манипулятора, концевым эффектором и захватом;
4. находится ли цель в рабочем пространстве захвата;
5. действительно ли объект поднимается после того, как захват закрылся;
6. может ли робот донести объект до мусорной корзины и отпустить его;
7. подтверждает ли оценщик успешное размещение, а не только то, что робот прошёл рядом с целью.

Поэтому в реализации навигация по координатам должна рассматриваться как промежуточный этап, а не как финальная цель задачи.
