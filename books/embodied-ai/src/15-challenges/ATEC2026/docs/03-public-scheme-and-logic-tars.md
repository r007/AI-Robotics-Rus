## 3.2 Почему стоит смотреть именно Logic-TARS

В README Logic-TARS заявлен результат `32/100`. Эта цифра — самооценка автора репозитория и не может считаться официальным результатом. Ценность для переноса в другом: проект отделяет интерфейс обучения, интерфейс развёртывания и высокоуровневую логику управления.

### Интерфейс обучения и развёртывания

Основной контракт можно описать так:

```text
observation policy: 61D
action policy:      16D = 12D leg + 4D wheel
official action:    24D = 12D leg + 4D wheel + 8D Piper arm
```

Это означает, что действия руки не выбираются policy произвольно: в адаптере развёртывания они явно фиксируются или обнуляются. Так locomotion policy использует уже имеющиеся возможности шасси и при этом удовлетворяет официальному интерфейсу отправки.

### Курсовое обучение

Публичные скрипты показывают поэтапный маршрут:

```text
flat locomotion
  -> rough straight walking
  -> rough omni B2W
  -> Task D fine-tuning
  -> export
  -> official submission adapter
```

Этот маршрут полезно перенять как организацию обучения, но нельзя просто скопировать checkpoint. Разные машины с разными версиями Isaac Sim, ассетами робота, значениями суставов по умолчанию и random seed дают разное поведение policy.

### Высокоуровневый конечный автомат Task D

Точка входа в отправку включает такие стадии:

```text
approach box
  -> push box
  -> navigate platform
  -> climb finish
```

Переключение стадий опирается на текущую оценку, обнаружение ящика по LiDAR, расстояние, bearing и прогресс робота. По сравнению с одной командой скорости конечный автомат проще показывает, где именно произошёл сбой: при ходьбе, при контакте или на платформе.

### Информация о задаче в 61D observation

В публичном коде к базовым наблюдениям locomotion добавляется информация о задаче:

- нормированная текущая оценка;
- one-hot стадии оценки;
- видит ли LiDAR ящик;
- bearing ящика;
- нормированное расстояние до ящика.

Ключевая идея здесь в том, что policy получает одновременно «какой этап задачи уже пройден» и «где сейчас ящик», а не только состояние корпуса робота.

## 3.3 Что можно перенести

### Высокий приоритет

1. Контракт адаптации действий 16D → 24D.
2. Переключение стадий с учётом оценки.
3. Минимальный интерфейс обнаружения ящика по LiDAR: bearing и distance.
4. Блокировка курса и коррекция скорости.
5. Восстановление при застревании, если оценка долго не растёт.
6. Порядок обучения: flat → rough → донастройка под Task D.

### Нужно перепроверить

1. Какую именно машину использует наша ветка: B2Piper или B2wPiper.
2. Точный порядок каждого из 61 измерения относительно наших наблюдений.
3. Масштаб, знак и порядок четырёх колёс для wheel action.
4. Остаётся ли в текущей официальной версии допустимым обнуление фиксированных 8D действий Piper.
5. Совпадают ли пороги оценки с текущим официальным оценщиком.
6. Число лучей LiDAR, диапазон углов и параметры фильтрации по высоте.
7. Доступен ли внешний checkpoint и каковы его лицензия и зависимости от официальных ассетов.

## 3.4 Что нельзя переносить напрямую

- Нельзя копировать `submission/solution.py` в B2Piper.
- Нельзя считать конечный автомат ящика Task D контроллером захвата мусора для Task B.
- Нельзя предполагать, что глобальная камера или мировые координаты симуляции доступны при официальной отправке.
- Нельзя записывать самооценку `32/100` как официальный рейтинг Datawhale.
- Нельзя выдавать репозиторий без checkpoint за готовое к запуску решение с высоким баллом.
